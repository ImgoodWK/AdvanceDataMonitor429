## 3. 当前基线与保护要求

截至 2026-07-20，工作区有大量正在开发且未提交的 WebAE、截图、渲染、QQ、AI、Spark 和服务端后台改动。后续 Agent 必须把它们视为用户工作，不得回滚。

已知基线：

- 前端为 React 18 + TypeScript + Ant Design 5 + Vite 5。
- WebAE 后端由 NanoHTTPD + `WebApiRouter` 提供 REST/SSE。
- 当前认证包含 owner、guest、管理员设备授权和按网络 allow/deny。
- 当前自动化动作只有 `craft_when_below`，并已有冷却、每小时上限和 Tick 限幅。
- 当前 PWA 只有 manifest、移动 meta 和响应式样式，没有 Service Worker、离线应用壳或 Web Push。
- 当前 URL 支持 `page` 与 `network(s)`，但 `admin` 未列入 `VALID_PAGES`，且页面切换使用 `replaceState`，没有完整的历史导航语义。
- 当前测试有 Java 单元测试与 Vitest 工具/状态测试，但没有仓库级 Playwright E2E。

开始每个阶段前必须重新运行基线检查，不能沿用本文件中的历史结果：

### 5.1 阶段 0A：冻结主题扩张

实施项：

2. 在 `ThemeStudio` 和设置页保留搜索、分类、收藏、混搭和导入导出，不移除功能。
3. 后续允许的主题改动仅限：可访问性修复、内容遮挡修复、响应式修复、性能修复、现有 ID 迁移和文案修复。
4. 测试继续验证 ID 唯一、引用有效、设计包指向存在；不要用会阻止合法修复的脆弱 CSS 全量快照。
5. 在 PR 模板或 Agent 规则中要求新增主题必须由用户重新明确授权，不能从本路线图推断授权。

验收：

- 现有主题数量和用户数据兼容性不变。

### 5.2 阶段 0B：URL 深链与浏览器历史

目标：刷新、复制链接、前进和后退后仍停留在正确的 WebAE 上下文。

优先复用：

- `context/AppContext.tsx`
- `utils/urlNavigation.ts`
- `components/Layout/navConfig.ts`
- `components/Layout/AppLayout.tsx`
- 各页现有 `activeTab`、搜索预填和网络选择状态

实施项：

1. 让合法页面来源单一化，避免 `PageId`、`NAV_PAGES` 和 `VALID_PAGES` 三处漂移。
2. 修复 `admin` 深链；保留 `diagnostics` 旧链接兼容，可规范化为管理控制台的 diagnostics 标签。
3. 区分用户导航和状态规范化：用户换页使用可回退的历史记录，初始化/纠错使用替换。
4. 监听 `popstate`，恢复 page、network(s) 和已纳入契约的 tab。
5. 第一版只加入稳定且有价值的子状态：`page`、`tab`、`network`/`networks`、搜索词；不要把临时 Modal、Token、密钥和大段 JSON 写入 URL。
6. 删除或迁移 `window.location.hash = '#settings'` 等与 query 路由冲突的旧写法。
7. 未授权用户打开管理员深链时显示现有拒绝界面，不静默跳转，也不泄露管理员数据。

测试：

- 新增 `urlNavigation.test.ts`：合法/非法 page、单/多网络、admin、legacy diagnostics、编码、清理。
- 组件/E2E：直接打开深链、刷新、前进、后退、未授权 admin、网络不存在时降级。
- 确认 URL 中永远没有 Bearer Token、管理员 Token、AI Key 和告警凭据。

验收：

- `?page=admin&tab=diagnostics` 刷新后状态保持。
- 页面 A → B → C 后，浏览器后退能回到 B 和 A。
- 深链测试可在 `5174` 开发环境和 `8090` 内嵌环境通过。

### 5.3 阶段 0C：浏览器 E2E 与无障碍基线

注意：`@playwright/mcp` 让 Agent 操作浏览器；`@playwright/test` 才是可提交、可在 CI 重复执行的测试，两者不能互相替代。

实施项：

1. 为 `webae-frontend/` 增加 Playwright Test 配置、脚本和独立测试目录。
2. 建立两层测试：
   - 确定性测试：固定 API fixture/mock，验证导航、空态、错误态和权限态。
   - 本地真实冒烟：连接 `8090`，只在专用测试世界和专用 Token 上运行。
3. 最小页面矩阵：登录、Dashboard、Storage、Recipes、Settings、Admin/Diagnostics、Alerts、Project/History（实现后追加）。
4. 最小权限矩阵：未登录、owner、guest/viewer、具名角色、admin。
5. 最小视口矩阵：1440×900、1024×768、390×844。
6. 加入控制台 error、未捕获 Promise、白屏、主要 API 5xx、文本溢出和关键控件可见性断言。
7. 加入键盘导航、焦点可见、Modal Esc、图标按钮 aria-label 和 reduced-motion 检查。
8. 真实写操作默认禁止；下单、样板、任务领取、命令、Runbook 执行只能在明确标记的隔离测试中运行。

建议脚本：

```json
{
  "test:e2e": "playwright test",
  "test:e2e:ui": "playwright test --ui",
  "test:e2e:live": "playwright test --project=live"
}
```

CI 要求：

- mock E2E 可进入 GitHub gate。
- live E2E 不依赖真实玩家世界，不作为普通 PR 强制门禁；可由本地或专用环境运行。
- 失败时保留 trace、截图和最小控制台日志，不保存 Token。

## 6. 阶段 1：细粒度角色与 API Token

### 6.1 目标

把 owner/guest/admin 的粗粒度模型升级为“身份 + 角色 + scope + 网络范围 + 有效期”，同时保持旧 Token 可迁移和可撤销。

### 6.2 建议权限模型

先冻结机器可读 scope 名称，再写 UI。建议最小集合：

| 领域 | Scope |
|------|-------|
| 基础数据 | `data.read` |
| 聊天 | `chat.read`、`chat.write` |
| 合成订单 | `orders.read`、`orders.submit`、`orders.cancel` |
| 样板 | `patterns.read`、`patterns.write` |
| 任务 | `quests.read`、`quests.submit`、`quests.claim` |
| 拓扑/地图 | `topology.read`、`topology.capture` |
| 告警 | `alerts.read`、`alerts.manage` |
| 历史/事件 | `history.read`、`incidents.manage` |
| 工厂项目 | `projects.read`、`projects.edit`、`projects.execute` |
| 自动处置 | `runbooks.read`、`runbooks.manage`、`runbooks.approve` |
| 运维 | `spark.run`、`console.execute`、`players.manage`、`integrations.manage` |
| 授权 | `tokens.manage`、`roles.manage` |

内置角色建议：Viewer、Operator、Production Engineer、Quest Helper、Maintainer、Admin。角色只是 scope 模板，网络 allowlist/deny 仍独立生效。

### 6.3 服务端实施

1. 新增集中式授权入口，例如 `WebAuthorization.require(auth, scope, networkKey)`；禁止每个 Handler 自己拼判断。
2. API Token 使用随机值，完整值只显示一次；磁盘只保存 token ID、前缀、强哈希、角色/scopes、网络范围、创建者、创建/到期/最后使用时间。
3. API Token 与现有管理员 grant 分开迁移，不能把管理员 Token 降级成普通 Token，也不能自动扩大 guest 权限。
4. 旧 owner/guest Token 在兼容期映射到明确的 legacy 角色；服务端响应加入迁移提示但不强制立即失效。
5. 所有写端点逐项声明所需 scope；管理员路由不再仅依靠统一 `isAdmin` 布尔值。
6. 对 token 创建、轮换、撤销、角色变更、拒绝访问写入事件审计，但绝不记录 token 明文。
7. 增加每 actor 的创建/验证/失败限流，比较哈希时避免明显的时序泄漏。

### 6.4 API 与前端

建议先提交 OpenAPI 风格契约草案，再落地路由：

- `GET/POST /api/auth/api-tokens`
- `DELETE /api/auth/api-tokens/{id}`
- `POST /api/auth/api-tokens/{id}/rotate`
- `GET/PUT /api/auth/roles`
- `GET /api/auth/capabilities`

前端要求：

- 设置页新增角色/API Token 管理，仅具备对应 scope 的用户可见。
- 创建完成后只显示一次完整 Token，提供复制和“我已保存”确认。
- 清楚展示角色、scope、网络、到期时间、最后使用、创建者和撤销状态。
- 不把 API Token 放入 UI 备份、Preset、URL、日志、错误上报或浏览器通知。

### 6.5 迁移与验收

- 迁移前备份 `web-tokens.json`、管理员 grant 和 ACL 文件；写入使用临时文件 + 原子替换。
- 至少覆盖每个写 Handler 的允许/拒绝测试，并验证网络 deny 高于角色 allow。
- 旧 Token、guest allowlist、停用玩家、停用网络、管理员设备授权全部有回归测试。
- 文档明确 Token 泄露后的吊销与紧急 rotate 操作。

## 7. 阶段 2：历史与事件中心

### 7.1 产品目标

把目前分散的短窗口趋势、告警历史、订单历史、Spark 记录和后台审计统一到一条可查询、可关联、可确认的时间线。

第一版必须回答：

- 某个网络在指定时间段发生了什么？
- TPS/MSPT、电力、库存、CPU、GT 状态在事件前后如何变化？
- 哪个玩家、Token、自动规则或外部集成触发了动作？
- 事件是否已确认、由谁处理、是否恢复？

### 7.2 数据分层

建议优先使用 Java 标准库可实现的有界分段存储，避免给 1.7.10 模组引入原生数据库：

- 当前窗口：内存 ring buffer。
- 落盘：按小时/天分段的 JSONL 或压缩段文件，后台单线程批量写入。
- 下采样：原始 1 分钟点保留 24 小时，5/15 分钟聚合保留 7～30 天；具体值由 Config 限幅。
- 磁盘预算：按 owner、网络和全局设置最大 MiB，超限先删最老分段。
- 查询：先读内存和段索引，再按时间范围加载；HTTP 线程不得解析无界历史。

任何改用 SQLite/其他数据库的方案必须先提交 ADR，说明发布 jar、Java 版本、并发、损坏恢复和无原生依赖替代方案。

### 7.3 指标与事件

首批指标：TPS、MSPT、在线人数、EU/蒸汽存量与速率、存储种类/字节、CPU 忙碌、GT 活跃/异常、告警数量。物品/流体明细只记录用户钉选或规则引用项，禁止全量库存持续落盘。

首批事件：

- 告警触发/恢复/投递失败。
- 订单提交/完成/失败/取消和自动补货。
- 样板新增/编辑/删除/注入。
- 任务提交/领取。
- Spark 开始/结束/分析。
- 服务端后台命令。
- Token、角色、ACL、网络停用变更。
- 工厂项目和 Runbook 生命周期事件。

统一事件字段至少包含：`id`、`timestamp`、`type`、`severity`、`ownerUuid`、`networkKey`、`actor`、`source`、`correlationId`、`summary`、`detailsRef`、`status`。

### 7.4 Incident 模型

- 支持从告警或事件创建 Incident。
- 状态：open、acknowledged、investigating、resolved、closed。
- 支持负责人、备注、标签、关联 Spark/订单/网络/Runbook。
- 自动聚合只能提出候选，不得错误地自动关闭事故。
- 所有确认、指派、备注和关闭动作写入不可变事件记录。

### 7.5 API/前端建议

- `GET /api/history/series?metric=&from=&to=&step=&network=`
- `GET /api/events?from=&to=&type=&severity=&actor=&network=&cursor=`
- `GET /api/events/{id}`
- `GET/POST/PATCH /api/incidents`
- `GET/PATCH /api/incidents/{id}`

优先把现有“告警历史”入口升级为“事件中心”，避免再增加一个孤立一级页面。页面包含时间范围、网络、类型、严重级别、actor 筛选，趋势图与事件时间线共用同一横轴。

### 7.6 性能与验收

- 空闲时不得新增世界/AE 全量扫描；只消费已有采样器、业务动作和告警产生的事件。
- 写队列有容量、丢弃计数和诊断；高严重级事件优先于普通指标点。
- 所有查询有时间范围、点数、游标和响应体积上限。
- 服务器重启、损坏尾段、磁盘满、时钟回拨和旧数据迁移都有测试。
- Diagnostics 能看到事件写队列、落盘耗时、查询 Top/慢请求和丢弃计数。

## 8. 阶段 3：工厂项目计划

### 8.1 产品目标

在现有 Planner、配方缓存、材料树、样板浏览和 AE 下单之上，提供长期生产目标，而不是再造一套配方或下单系统。

典型流程：

```text
创建目标物品与数量
  -> 选择网络和可接受配方
  -> 计算材料、已有库存、可合成量、缺失样板与阻塞项
  -> 用户确认阶段计划
  -> 分批提交 AE 订单
  -> 追踪完成、失败、库存变化和重新规划
```

### 8.2 复用边界

- 配方只读 `RecipeCacheStore` / 浏览器本地配方库。
- 材料展开复用 `CraftTreeCalculator`。
- 可用样板复用 pattern browse/grid detail。
- 订单提交复用 `OrderSubmitService` 和既有安全边界。
- 进度复用现有订单历史，不新增第二套 crafting tracker。
- Factory Flow 导出复用现有 Planner 导出能力。

### 8.3 数据模型

项目至少包含：ID、名称、owner、网络、目标列表、配方选择、计划版本、阶段、依赖、估算、创建者、状态、时间戳。

状态建议：draft、ready、running、blocked、paused、completed、cancelled。

第一版估算必须标为“估算”而非承诺：

- 已有/缺少材料。
- 可直接合成和缺失样板。
- AE CPU 候选与存储/协处理器约束。
- 已知配方时间/能耗可用时给出范围；未知时明确显示 unknown。
- 库存或样板快照版本变化后标记计划 stale，要求重新计算或确认继续。

### 8.4 安全执行

- 计算、预览、导出是只读动作。
- 提交订单必须由具备 `projects.execute` + `orders.submit` 的用户显式确认。
- 默认分批执行，设置单批物品数、并发订单数和失败停止策略。
- 不做虚假的硬库存锁定；若实现 reservation，必须明确它是 WebAE 逻辑预留，并处理外部终端消耗导致的漂移。
- 取消项目只停止未提交阶段，不得声称已取消 AE2 中无法撤回的实际加工。

### 8.5 UI/API 与验收

优先扩展现有 Planner 页面为项目工作区，提供列表、依赖图、材料表、阻塞项和执行时间线。

建议 API：

- `GET/POST /api/projects`
- `GET/PATCH/DELETE /api/projects/{id}`
- `POST /api/projects/{id}/plan`
- `POST /api/projects/{id}/execute`
- `POST /api/projects/{id}/pause`
- `POST /api/projects/{id}/replan`

测试至少覆盖：循环配方、多产物、替代配方、缺失样板、库存变化、跨网络拒绝、重复提交幂等、部分失败和服务器重启恢复。

## 9. 阶段 4：告警处置手册

### 9.1 产品目标

把“告警后人工到处找页面”升级为受控 Runbook：识别上下文、给出步骤、收集证据，并在权限和确认允许时执行有限动作。

### 9.2 安全等级

| 等级 | 示例 | 默认策略 |
|------|------|----------|
| 只读 | 查询健康、抓取已有快照、生成事件摘要、打开相关页面 | 可自动 |
| 低风险 | 创建 Incident、添加标签/备注、追加通知 | 可按规则自动 |
| 受控写入 | 创建工厂项目、提交已声明物品的补货、启动短时 Spark | 默认要求批准 |
| 高风险 | 任意控制台命令、停服、封禁、OP、白名单 | 永不提供自动动作 |

### 9.3 Runbook 模型

- Trigger：告警类型、严重级别、网络、持续时间和恢复条件。
- Conditions：TPS/MSPT、库存、CPU/GT 状态、冷却、时间窗、角色审批。
- Steps：说明、只读采集、通知、Incident 操作、受控动作。
- Approval：无需、单管理员、指定角色；不得用 QQ 机器人管理员替代 Minecraft/WebAE 权限。
- Guard：幂等键、冷却、每小时上限、最大并发、超时、重试策略。
- Result：每一步的开始/结束、actor、输入摘要、结果和失败原因写入事件中心。

### 9.4 首批模板

1. 低 TPS：创建 Incident → 采集健康/diagnostics → 建议或批准后启动短时默认 Spark → 关联结果。
2. CPU 卡住：读取订单/CPU/材料缺口 → 展示处理建议；不自动取消全部订单。
3. 库存不足：读取规则和材料树 → 创建补货项目 → 批准后按现有限幅提交。
4. GT 异常：关联机器、配方、网络、电力和最近事件 → 通知负责人。
5. 外部投递熔断：创建运维事件 → 展示队列和目标状态 → 人工测试已保存目标。

### 9.5 实现约束与验收

- 把现有 `craft_when_below` 迁移为兼容的内置 Runbook 或保留适配层，不能产生重复补货。
- Runbook 引擎只调白名单 action registry，不接受任意类名、URL 或命令文本。
- 主线程动作复用 `HandlerTick.enqueueServerTask`，外部网络复用现有有界投递队列。
- 提供 dry-run：展示匹配原因、将执行步骤和所需权限，不产生副作用。
- 提供全局 kill switch 和单 Runbook 禁用。
- 测试并发触发、重复事件、恢复后重触发、审批过期、队列满、重启恢复和权限撤销。

## 10. 阶段 5：真正的 PWA 与 Web Push

### 10.1 目标与定义

完成后才能在文档中把 WebAE 称为完整 PWA：

- 有受版本管理的 Service Worker 和应用壳缓存。
- 能明确处理更新、旧缓存和回滚。
- 断网时能打开应用并查看最近一次允许离线保存的只读快照。
- 页面关闭后，已订阅设备能收到服务器 Web Push。
- 在非 localhost 环境明确要求 HTTPS。

### 10.2 Service Worker

实施前在 ADR 中比较自定义 Service Worker 与 Workbox/vite-plugin-pwa，并验证 Vite 5、当前 Node、离线内嵌路径和构建产物兼容性。

硬边界：

- CacheStorage 只缓存静态应用壳和带 hash 的公开资源，禁止缓存带 Authorization 的 `/api/*` 响应。
- 离线数据存入按 owner/actor 隔离的 IndexedDB；退出登录、换 Token、账号停用时清除或隔离。
- 离线模式只读，绝不排队下单、样板、任务、命令、Runbook 或管理员写操作。
- 更新采用显式“有新版本，重新加载”提示；不要在用户编辑规则/项目时强制刷新。
- Service Worker 注册失败不得阻止普通在线 WebAE 使用。

### 10.3 Web Push

服务端需要：

- 生成/导入 VAPID 密钥，私钥只在服务端配置/密钥文件保存，API 永不回传。
- 保存与 owner、actor、设备标签、事件过滤器关联的 PushSubscription；提供订阅、更新和撤销。
- 复用告警投递的有界队列、重试、熔断和诊断，不在 Tick 线程做加密/HTTP。
- 处理 404/410 自动失效订阅，限制每 actor 设备数和推送频率。
- 默认 Push 载荷不含敏感库存、玩家坐标、命令输出和 Token；通知点击后打开页面并在重新认证后读取详情。

前端需要：

- 只能由明确用户手势请求 Notification/Push 权限。
- 展示浏览器支持、安全上下文、权限、订阅设备和最近投递状态。
- 支持按事件/严重级别过滤并单设备撤销。
- localhost 可开发；局域网 IP 的 HTTP 页面明确提示必须配置 HTTPS 反向代理。

### 10.4 测试与验收

- Playwright：首次安装、在线刷新、离线重开、旧缓存升级、权限拒绝、退出清数据、移动视口。
- Service Worker 单元测试：缓存版本、路由策略、消息协议、失败降级。
- 服务端：订阅校验、VAPID 密钥边界、410 清理、队列满、过滤和限流。
- 安全检查：API/CacheStorage/IndexedDB/日志/通知中无 Token 和密钥。
- 文档把“当前 manifest-only”改为实际完成能力；未完成前不得提前宣称后台 Push 或离线可用。

## 11. 跨阶段非功能要求

### 11.1 性能预算

- 空闲 Tick 不增加世界或 AE 全量扫描。
- 新 HTTP 路由全部进入 `topRoutes`/`slowHttp`。
- 新采集进入 `recordCollect`；新 Tick 阶段进入 `endPhase`。
- 所有历史/列表端点必须分页或游标化，响应有服务端硬上限。
- 所有后台队列展示深度、成功、失败、丢弃、超时和熔断指标。

### 11.2 安全预算

- 默认 `bindAddress=127.0.0.1` 不变。
- Token、VAPID 私钥、AI Key、QQ/微信/SMTP 凭据不进入 URL、日志、导出、Push 载荷和前端持久化。
- 所有修改型 AI、Project、Runbook 操作继续使用服务端候选/确认或等价的不可伪造确认机制。
- 权限检查必须在服务端；前端隐藏按钮只能改善体验，不能作为安全措施。

### 11.3 兼容与迁移

- 所有持久化结构带 `schemaVersion`。
- 读取旧版本、写新版本；迁移失败保留原文件并返回可诊断错误。
- 新功能默认关闭或只读上线，再逐步开放写操作。
- 删除字段/路由前至少保留一个迁移周期的兼容层和文档说明。

## 13. 完成定义

一个阶段只有同时满足以下条件才可标记完成：

1. 代码、DTO、API、权限和持久化迁移已落地。
2. Java/Vitest/Playwright 中与风险相称的测试通过。
3. TypeScript 检查和 WebAE 正式构建通过。
4. 文档一致性检查零错误；中英文档、manual、lang、rules 已同步或明确不适用。
5. 新路由和后台队列能在 Diagnostics 中观察。
6. 在桌面与移动视口做真实浏览器冒烟，无白屏、严重控制台错误、内容重叠和 Token 泄露。
7. 已检查最终 diff，没有覆盖用户的未提交改动。
8. PR/交接说明包含启用方法、回滚方法、迁移行为和剩余风险。

标准验证命令：

```powershell
Set-Location webae-frontend
npm.cmd test -- --run
npm.cmd exec tsc -- --noEmit
npm.cmd run build
Set-Location ..
.\gradlew.bat test
python tools/doc-check/doc-consistency-check.py
```

浏览器验收按 [浏览器联调环境配置计划](浏览器联调环境配置计划.md) 执行。
