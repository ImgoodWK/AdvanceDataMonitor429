## 1. 概述

WebAE 控制台是 TeXTech 模组内嵌的 **浏览器可访问** HTTP 管理面板。玩家可以通过任意现代化浏览器，实时查看服务器端的 AE2 存储状态、电力/蒸汽消耗速率、GT 机器运行情况、搜索 NEI 配方、编辑 AE2 样板，以及批量提交 AE2 合成订单。

技术栈：
- **服务端**: NanoHTTPD 轻量级 HTTP 服务器，嵌入 Minecraft 服务端进程
- **前端**: React 18 + TypeScript + Ant Design 5 单页应用（SPA），Vite 5 构建，内联 SVG 图表（`ChartTrendSvg` 等），通过 Fetch API 调用 REST 接口；完全离线打包（无 CDN 依赖）
- **渲染**: MVC 模式，后端只返回 JSON，所有 UI 由浏览器端 React 渲染

## 2. 架构总览

```
浏览器 (React + Ant Design + 内联 SVG 图表)
    ↓ HTTP REST API (JSON, Bearer Token)
[ NanoHTTPD 服务 ]
    ↓ CountDownLatch 主线程采集
[ HandlerTick 任务队列 ]
    ↓
[ AE2 API / GT API ]
```

核心数据流：

1. **HTTP 请求进入**：NanoHTTPD 工作线程解析 URL/method，经 `WebApiRouter` 分发到对应的 handler
2. **主线程数据采集**：所有需要访问 Minecraft 世界状态的操作（AE2 网络查询、GT 机器状态读取、样板注入等）通过 `CountDownLatch` 阻塞 HTTP 线程，将任务提交到 `HandlerTick` 主线程任务队列，完成后唤醒 HTTP 线程返回结果
3. **快照缓存**：高频轮询的存储/电力数据通过 `SnapshotScheduler` 定时在主线程采集后缓存，HTTP 请求直接读取缓存，避免每次阻塞主线程

## 7. 线程模型

核心挑战：Minecraft 服务端逻辑 **必须在主线程执行**，但 NanoHTTPD 在独立工作线程中处理 HTTP 请求。

解决方案：**CountDownLatch 主线程调度模式**

```java
// 伪代码示例
public SnapshotResult getSnapshot() {
    CountDownLatch latch = new CountDownLatch(1);
    SnapshotResult[] result = new SnapshotResult[1];

    HandlerTick.enqueueServerTask(() -> {
        result[0] = collectSnapshot();  // 在主线程采集
        latch.countDown();
    });

    latch.await(timeout, TimeUnit.SECONDS);
    return result[0];
}
```

三类采集策略：

| 策略 | 适用场景 | 阻塞 HTTP 线程？ |
|------|---------|-----------------|
| **缓存直读** | 存储/电力/GT、networks、P2P、cells、monitor bindings、scanner、patterns 富列表与 browse（`SnapshotScheduler` 定时采集） | 否 |
| **主线程实时查询** | 订单提交、样板注入/写操作、拓扑 POST 捕获、助手等 | 是（≤5–15 秒超时） |
| **客户端上传** | 配方数据（`PacketWebRecipeUpload` C→S） | 直接写入服务端缓存 |

`CountDownLatch` 超时默认 5 秒，超时后返回 HTTP 503。

## 8. 安全模型

- **Token 认证**：每位玩家一个随机 UUID，持久化到 `TeXTech/WebAE/web-tokens.json`（重新签发替换旧 Token）。TTL 可选，由 `tokenLifetimeHours` 控制（0=永不过期）
- **强制认证**：所有 `/api/` 端点都需要 `Authorization: Bearer <token>`，无关闭配置。401 响应带 `code` 字段（`missing_token`/`invalid_format`/`empty_token`/`token_expired`/`invalid_token`）
- **管理员专用端点**：`POST /api/refresh`、`/api/refresh/batch`、`/api/power/refresh`、`/api/power/refresh/batch`、`/api/gt/machines/refresh`、`/api/gt/machines/refresh/batch` 要求 OP 等级 >= 2（由 `WebAuthOpCheck` 校验）；非 OP 返回 403 + `code:admin_required`
- **默认本地绑定**：`bindAddress=127.0.0.1` 仅允许本机浏览器访问
- **无 HTTPS**：NanoHTTPD 不提供 TLS。局域网使用时通过 SSH 隧道或反向代理提供加密
- **Token 管理**：`/textech web issue`（自己）、`/textech web revoke [玩家]`（自己/OP）、`/textech web list`（OP）、`/textech web refresh [网络]`（OP，阶段 1.2）
- **不存储密码**：用户只需 Token 即可访问，不需要 Minecraft 账号验证

**安全警告**：
- `bindAddress=0.0.0.0` 会将控制台暴露给局域网所有设备，任何持有 Token 的人可查看存储、提交合成
- 建议在服务器防火墙层面限制端口访问

| 28 | `PacketWebIconUpload` | C→S | 客户端物品/流体图标分批上传（itemId → base64PNG，复用分片模式） |
| 29 | `PacketWebIconUploadAck` | S→C | 服务端图标上传确认（回传 receivedChunks/totalChunks/success/message） |
| 30 | `PacketWebUploadTrigger` | S→C | 服务端命令触发客户端开始 recipes/icons 上传（`/textech web recipes upload`、`/textech web icons upload`） |

配方上传流程：
1. 客户端 `KeyBindings.uploadNeiRecipes(scope, snapshotItemIds)` 混合采集：`NeiRecipeCollector`（主线程；`deep` 启用物品驱动扫描）或 `RecipeSnapshotCollector`（`snapshot` 范围）+ `GameRecipeCollector`（后台），去重合并（NEI 优先）为**单次会话**
2. 首批 `isStart` 时 `RecipeUploadSession.onStart()` 决定是否 `clearMemoryOnly()`（每位玩家仅首个活跃会话清缓存；重叠上传忽略）
3. `RecipeUploadThrottler` 按 `recipeUploadBatchesPerTick` 节流客户端上传；经 `RecipeUploadBatcher` 按 FML 32KB 上限安全分片（默认 JSON ≤ ~32KB−512B，超大配方自动裁剪 grid/rawJson）
4. 服务端 `RecipeCacheStore.ingest()` + 末批 `rebuildHandlerCounts()`；异步去抖写盘：`web-recipes.json` + `web-recipes.meta.json` + `recipe-chunks/chunk-NNNN.json`；默认 `recipeKeepMemoryAfterUpload=false` 写盘后清堆
5. 客户端 `RecipeLocalExporter` 同步写入 `<实例根>/TeXTech/WebAE/web-recipes.json`（纯 JSON，无 gzip）
6. 全部完成后发送 `PacketWebRecipeUploadAck` 确认；浏览器需在配方页点「获取配方」经 sync API 拉入 IndexedDB

图标上传流程：
1. 客户端 `IconRenderer`（@SideOnly CLIENT）每帧离屏渲染若干物品为 32×32 PNG
2. 打包为 IconBundle（itemId → base64PNG），通过 `PacketWebIconUpload` 分片上传
3. 服务端解码写盘到 `TeXTech/WebAE/icons/<packName>/`，调用 `IconStore.recordDefaultPack` 记录最近上传 pack
4. `PacketWebIconUploadAck` 回传进度

命令触发上传流程（ID 30）：
1. OP 玩家执行 `/textech web recipes upload` 或 `/textech web icons upload`
2. `CommandWebConsole` 校验 OP（`canUseOpCommands`）与玩家身份，发送 `PacketWebUploadTrigger`（S→C，字段 uploadType=recipes/icons、packName）
3. 客户端 handler 调用 `KeyBindings.uploadNeiRecipes()` 或 `KeyBindings.triggerIconUpload(packName)` 这两个 public static 入口
4. 后续走与命令相同的上传链路（ID 26/28）

详见 `network-packets.mdc`。

### 11.1 存储监控

- **Handler**: `StorageHandler.java`（全量快照）、`StoragePagedHandler.java`（cursor 分页）
- **采集器**: `AeSnapshotCollector.java` 在主线程读取 AE2 网络存储统计
- **缓存**: `SnapshotCache` TTL = `webRefreshIntervalMs * 3`（容许采集抖动）；`snapshotVersion()` 供 cursor 失效检测
- **调度器（阶段 1.2）**: `SnapshotScheduler` 每 `refreshIntervalMs` 采集一次，分摊到多个 tick（每 tick 处理 `ceil(activeKeys / N)` 个，`N = intervalMs / 50`），只采集最近 2 分钟活跃的网络
- **返回数据**: items / fluids / essentia / bytes used+max / 合成处理器（`CpuEntry` 含坐标、监视器位置、remainingItems/startItems 等，Phase 3 扩展）
- **端点**: `GET /api/storage`（只读缓存，未命中返回上次快照）、`GET /api/storage/batch`、`GET /api/storage/items|fluids|essentia`（cursor 分页，默认 limit=200，sort=`amount_desc|amount_asc|name_asc|name_desc`，search 过滤；409 `cursor_stale`）、`POST /api/refresh`（管理员）、`POST /api/refresh/batch`（管理员）
- **前端**: 存储页物品/流体/源质 Tab 使用 `useStoragePaged` + `VirtualStorageTable`（`@tanstack/react-virtual` 行虚拟化 + 无限滚动）；搜索 300ms 防抖；排序切换重置 cursor；合并模式 ≤3 网络客户端 merge，>3 网络提示切换单网；顶部 `OverviewWidgetGrid` 使用分页 API 的 `totalEstimate`/`totalAmountSum` 计数（`OverviewSnapshot.itemCount` 等覆盖字段）；`useSnapshotData` 切换网络时 stale-while-revalidate（保留 per-network 缓存 + `refreshing` 指示）。CPU 独立菜单见 [11.14](#1114-存储总览可配置与-cpu-独立页面phase-3)

### 11.4 配方搜索

- **数据流**: OP `/textech web recipes upload*` → 服务端磁盘权威（不启动全量入内存）→ 玩家浏览器点「获取配方」→ IndexedDB 本地浏览/搜索
- **Handler**: `RecipeHandler.java`（含 sync manifest/chunk + 服务端 browse/search 兜底）
- **混合采集（客户端）**: `KeyBindings.uploadNeiRecipes(scope, …)` 先 `NeiRecipeCollector.collectAll(deepScan)` 或 `RecipeSnapshotCollector.collectForItems()`（客户端主线程），再 `GameRecipeCollector.collectAll()`（后台线程）；按 `handlerId:recipeIndex` 去重，NEI 优先；经 `RecipeUploadThrottler` 合并为单次上传会话
- **上传会话**: `RecipeUploadSession` 确保每位玩家仅首个 `isStart` 批次清空内存；并发重叠上传被忽略
- **NEI 解析**: `NeiRecipeCollector.extractRecipe()` 反射 `PositionedStack`；`handlerName` 经 `RecipeDisplayNames` 格式化为 `本地化名 (langKey)`；`itemId` 含 meta（`registry:meta`）
- **Game 采集**: `GameRecipeCollector` 为 ShapedRecipes 写入 grid；GT RecipeMap 写入流体与 EU/耗时；handler 显示名同上
- **上传**: `PacketWebRecipeUpload` 分批 C→S；结束时 `rebuildHandlerCounts()` 修正 handler 计数
- **缓存 / 磁盘**: `RecipeCacheStore` — 无启动全量加载；`ensureLoaded()` 懒加载（HTTP 线程可阻塞；**Server tick 线程只启动** `WebAE-RecipeCache-Load` 后台加载并立即返回，禁止同步解析全量 JSON）；任务书 analysis/submit 等在 HTTP 侧预 `ensureLoaded`；材料树在主线程且内存未加载时跳过展开；写盘产出 `web-recipes.json` + `web-recipes.meta.json`（`RecipeDiskMeta`）+ `recipe-chunks/chunk-NNNN.json`（大小由 `recipeSyncChunkSize`）；默认 `recipeKeepMemoryAfterUpload=false` 写盘后清堆；`recipeCacheMode`（GTNH 默认 `full`）仅在内存已加载时生效；模糊搜索兜底由 `RecipeSearchRateLimiter` 限流
- **Sync API**（主路径，不强制加载全量入堆）:
  - `GET /api/recipes/sync/manifest` — revision / chunkCount / handlers
  - `GET /api/recipes/sync/chunk?index=N` — 单块配方数组
- **服务端兜底 API**（材料树等；`ensureLoaded`）:
  - `GET /api/recipes/browse|search|suggest|…`
- **DTO 扩展**: `RecipeDto` 含 `gridSlots`、`gridWidth/Height`、`euPerTick`、`durationTicks`、`voltageTier`、`recipeType`
- **前端** (`webae-frontend/src/pages/Recipes.tsx` + `hooks/useRecipeSync.ts` + `utils/recipeLocalStore.ts` + `components/recipes/`)：
  - 工具栏 **「获取配方」**：对照 manifest revision，按块拉取并写入 IndexedDB；进度条可取消；revision 未变不自动重下
  - 获取完成后 **本地** 浏览/模糊搜索/补全；类别筛选、完整/合并、缩略/详细布局同前
  - **无限滚动**懒加载本地库；缩略/合并卡片 + `RecipeDetailModal`；详细视图合成格/流体/GT Tag
  - 布局切换 CSS 显示/隐藏 + `React.memo`；持久化 `localStorage.webae-recipe-layout` / `webae-recipe-display-mode`
- **清空**: `/textech web recipes clear` 清空服务端内存与磁盘（含 meta/chunks）；浏览器 IndexedDB 需各端自行清除或重新 Fetch 覆盖
### 11.5 样板管理

- **Handler**: `PatternHandler.java`（编码/注入/接口枚举）、`PatternListHandler.java`（样板总览/详情/删除/编辑回写）、`PatternBrowseHandler.java`（Grid+Interface 双源 browse 分页）、`PatternGridDetailHandler.java`（Grid 单条目完整 I/O）
- **Browse 缓存**: `PatternBrowseService.java` 分离「主线程 buildAndStoreCache」与「HTTP 线程 paginate」；`SnapshotScheduler` 对活跃网络按 `Config.webPatternCacheTtlMs` 后台预采集；GET 返回 `cached:true/false` + `timestamp`（过期仍返回 stale 数据）；owner 离线 browse 经 `getOwnerPlayerOrFake`；POST `/api/patterns/browse/refresh`（OP）强制重建；Web PUT/DELETE/inject 与 `PatternBrowseInvalidationGridCache`（监听 `MENetworkCraftingPatternChange`，`AdvanceDataMonitor.postInit` 经 `PatternBrowseGridCacheRegistrar` 注册）均调用 `invalidateAll()`
- **接口枚举**: `InterfaceLocator.java` 在主线程枚举所有 ME 接口终端；响应 DTO 含 `machineRecipeType`（机器名 + GT RecipeMap）与 `existingPatterns`（槽位/patternId/outputs/crafting）；反射访问器（`getPatterns`/`getTermName`/`getLocation`/`getInstalledUpgrades`/`saveChanges`）为 `public static`，供 `PatternListHandler` 复用

### 11.6 AE 合成下单（Phase 7 增强）

- **Handler**: `OrderHandler.java`
- **下单接口**:
  - 单物品 `/api/order`：body `{ networkId, itemName?, amount, rawText?, locale?, cpuName?, patternId? }`；`patternId` 优先于 itemName
  - 批量 `/api/order/batch`：body `{ networkId, cpuName?, items:[{ itemName, amount, patternId? }] }`（API 保留供内部/集成；**Web UI 不再暴露批量面板**）

- **真实进度**（`WebAeOrderProgressService`，按 `networkId` 读网格，**不**按玩家坐标搜 Link）:
  1. 下单时登记 `jobId`，`submitJob` 成功后绑定 `ICraftingLink` / `craftingId`

  5. 同网络短 TTL（约 50ms）CPU 快照缓存，多订单复用；**禁止** `populatePlan` / 物品明细遍历
- **列表/历史**: `GET /api/order/list` 返回 `{ success, orders, history }`；完成/取消/失败从 active 移入内存 `historyOrders`（最多 200 条，重启清空，**按 ownerUuid 隔离**）；`OrderStatus` 含 `cpuName`/`cpuInfo`/`finalProgress`/`itemName`/`amount`/`patternId`/`networkId`/`craftingId`/`startItems`/`remainingItems`/`progressKind=steps`

- **底层**: `WebAeCraftService` + `AssistantServerServices` + `AssistantCraftJobManager` + `WebAeOrderProgressService`

  - 顶部 CPU `Select`（名称 + 容量 + 并行数 + 忙碌/空闲）

### 11.20a 多渠道投递 + 服务器健康

- **本地渠道**: `browserNotifications` / `playerChat` / `playerHud` 共享 `events[]` + `severities[]` 过滤；聊天/HUD 通过 `HandlerWebPlayerTracker` O(1) 查 owner，HUD 使用 `PacketWebAlertNotify` ID 50 与 `WebAlertHudRenderer`
- **外部目标**: `notificationTargets[]` 类型为 `qq_official` / `wechat_official` / `email` / `wecom_bot` / `wecom_app`，可带 `ownerUuids[]`。旧 `webhooks[]` 继续兼容 Discord embed 与通用 JSON
- **QQ 目标 ID 探测**: `QqIdProbeService` + `QqGatewayClient`（shadow `Java-WebSocket`）由管理员 `POST /api/alerts/qq-id-probe/start` 触发；服务端主动连 QQ WSS 网关（无需公网 HTTPS 回调），解析 `C2C`/`GROUP`/`CHANNEL` 事件写入内存列表；`GET` 轮询、`POST .../stop` 结束；默认约 10 分钟超时。前端设置页「获取目标 ID」可一键填入 `targetType`/`targetId`
- **测试投递**: `POST /api/alerts/test` 仅接受已保存的目标种类与 ID，管理员显式点击后构造固定测试告警；允许在单项目标关闭时验证凭据，但服务端 `[webConsole] alertsEnabled=false` 时拒绝。返回“已入队”不承诺第三方最终送达，结果由投递计数、熔断状态和实际收件共同确认
- **平台适配**: QQ 使用 app access token 与 `/v2/groups|users/.../messages` 或 `/channels/.../messages`；公众号使用 `cgi-bin/token` + 客服/模板消息；企业微信支持群机器人与 `gettoken` + 应用 `message/send`；SMTP 原生支持 none/STARTTLS/SSL + AUTH LOGIN。`baseUrl`/`tokenUrl` 可覆盖以适应平台版本或代理
- **密钥边界**: URL、AppSecret、CorpSecret、SMTP 密码只存在服务端 JSON；`sanitizeForClient` 仅返回 `***` + 末 4 位及 `*Configured`，PUT 按目标 ID 合并未修改的掩码密钥
- **异步与背压**: `WebhookDispatcher` 固定 `ArrayBlockingQueue(512)` + 2 daemon worker；每告警 fan-out 默认最多 16；1–5 次重试、`Retry-After`/指数退避（封顶 30s）、连续失败熔断。队列满只丢外部投递并计数，不阻塞 Tick
- **TPS 分摊**: `WebAlertEngine` 每次告警阶段最多评估 2 个 owner，复用同网络 storage 快照和 item/fluid 索引；低 TPS 告警随 owner 轮转评估，避免每 200ms 全 owner 循环；`HandlerTick` 单独记录 `PHASE_ALERT_ENGINE`
- **事件类型**: `inventory_threshold` / `cpu_stuck` / `gt_error` / `order_complete` / `channel_overload` / `server_tps_below` / `automation_craft`
- **TPS 告警**: `serverTpsBelowEnabled` + `serverTpsThreshold`（默认 15）+ `serverTpsDurationSeconds`（默认 60）；`WebAlertEngine` 读 `ServerHealthSampler`
- **健康采样**: `webae/health/ServerHealthSampler.java` — 读 `MinecraftServer.tickTimeArray` 最近 100 tick 均值（与 `/forge tps` Overall 同公式：`mspt = mean(ns)×1e-6`，`tps = min(20, 1000/mspt)`）；`HandlerTick` 每 tick 刷新，约 1s 写入 300s 滚动窗口；`GET /api/server/health`（`ServerHealthHandler`）；性能诊断页顶部 TPS/MSPT 同源
- **性能诊断**: `webae/perf/WebAePerfProfiler.java` + `SnapshotWorkerPool` — tick 分段 / HTTP 路由 / 快照采集耗时；single-flight + `queueDepth≥48` 背压；500ms 软超时仅 WARN，持闸门至任务完成（硬等上限 30s）；`GET /api/server/diagnostics`（含 `snapshotWorkerBusy` / timeouts / skips）；`[debug] webaePerf` → `logs/textech/webae-perf.log`（慢 tick≥5ms / 慢 HTTP≥200ms 始终记一条）；前端 `pages/Diagnostics.tsx` + `useServerDiagnostics`。**新增 `/api/*` 必须接入诊断**，约定见 `.cursor/rules/webae-perf-diagnostics.mdc`。

### 11.27 Spark 性能分析集成

- **可选依赖**：`dependencies.gradle` 使用 Curse Maven 的 Spark Forge 1.7.10 文件（`curse.maven:spark-361579:3577247`），配置为 `compileOnly` 与 dev-only runtime；TeXTech 不捆绑 Spark，整合包仍需自行安装 `spark-forge1710.jar`。
- **运行时门控**：`SparkService.isEnabled()` 同时要求 `[webConsole] sparkEnabled=true` 与 Forge `spark` modid 已加载。两者任一不满足时 `/api/config` 返回 `sparkEnabled=false`，管理控制台不显示 Spark 标签，直接 API 返回 503。
- **采样模式与开销边界**：`server` 仅采样服务端游戏主线程（默认 4ms）；`lagSpikes` 使用 Spark `--only-ticks-over` 并以 `--order-by-time` 输出；`allThreads` 使用 `--thread * --not-combined --ignore-sleeping`，服务端强制间隔不低于 10ms。模式和数字参数在服务端白名单化/限幅，不拼接自由文本；启动前还检查 Spark 内部 sampler，拒绝接管游戏内手动启动的 profiler，活动记录也禁止直接删除。空闲时 ADM 不注册新 tick 阶段、不扫描世界、不轮询 ActivityLog；只有采样运行时前端每 3 秒读取内存状态，上传等待期由 daemon 线程每 2 秒短查一次 ActivityLog（最多 90 秒）。
- **命令桥接 / Viewer 修复**：Spark 1.6.4 的参数解析器要求 profiler 选项全部以 `--` 开头，且**没有** `start` 子命令；WebAE 因此通过服务端插件 `processCommand` 直接执行 `spark profiler --interval N ...`，到时执行 `spark profiler --stop`（慢 tick 模式附加 `--order-by-time`）。旧的 `spark profiler start/stop` 会在 Spark 的 `Arguments` 解析阶段失败，既不会采样也不会生成 ActivityLog，这正是历史记录一直无 Viewer 的根因。结果捕获依次使用聊天文本/click event、服务端 SparkPlatform 的内存 ActivityLog、`config/activity.json` 文件兜底；管理员还可通过 `/api/spark/recover` 对旧的无链接记录按需重查。
- **本地调用树分析**：停止命令执行前保存 Spark `SamplerModule.activeSampler` 引用，命令返回后反射读取 Java/async sampler 的 `dataAggregator.getData()`。WebAE 遍历 Spark 已聚合的 `ThreadNode` / `StackTraceNode`（不自行采样），以 `节点总时间 − 子节点总时间` 计算方法自身耗时，聚合前 50 个方法、前 16 个线程组和稳定类别（AE2、GregTech、机器/实体、区块/世界生成、网络/I/O、GC/JVM 等）。持久化只保存有界摘要；`analysisStatus` 区分 `pending/ready/empty/unavailable/legacy`，Spark 缺失时仍保持可选依赖安全。
- **上下文与持久化**：分析开始/结束各执行一次轻量 `spark tps`，保存 Spark 自身的 TPS/MSPT/CPU 输出用于前后对照；不会新增常驻指标采集。`SparkProfileStore` 以 bounded JSON 保存 `TeXTech/WebAE/spark-history.json`，包含模式、有效间隔、慢 tick 阈值、实际停止时间、本地热点/类别/线程摘要、上下文输出和可选 Viewer URL；服务器重启时未结束记录标为 `interrupted`，旧记录标为 `legacy`。
- **REST/前端**：`SparkHandler` 提供状态、详情、启动、停止、Viewer 恢复、删除和显式 AI 分析接口；高频 `GET /api/spark` 移除热点数组，只返回分析状态/计数与轻量元数据，点击详情或对比时才读取单条完整记录。`pages/Spark.tsx` 默认展示方法热点、影响分类、线程占比和基于独占占比/具体方法证据的确定性本地建议；管理员可再点击 AI 深度分析。外发载荷由 `SparkAiAnalysisService` 限定为前 20 热点、16 类别、12 线程和采样元数据，不含原始输出、Viewer URL、发起者或 API Key；两次采样统一按 `B − A`。官方 Viewer 只保留为折叠区中的可选深层火焰图入口。

### 11.28 WebAE AI 助手与密钥边界

### 11.30 客户端窗口截图与聊天附件

- **隐私边界**：`KeyBindings` 默认 F10，并用 ClientTick 原始按键边沿保证任意 `GuiScreen` 内可触发。`ClientScreenshotService` 只读取 Minecraft `Framebuffer`（路径与原版 F2 一致），不调用 AWT Robot、桌面或其他窗口 API；GL 读回在客户端渲染线程，缩放/JPEG/历史清理在单线程有界 daemon。

- **后台完成**：完整字节交给一个容量固定的后台处理器，仅读取 JPEG 头校验真实尺寸。Web 目标写入 `TeXTech/WebAE/chat-attachments/` 并在 `ChatMessage` 保存附件元数据；QQ 目标直接进入机器人有界队列，不在服务端留长期副本。队列成功只表示已接受，不承诺第三方最终送达。
- **WebAE**：聊天前端用 Bearer 鉴权 fetch Blob、Object URL 展示缩略图，并由 Ant Design `Image` 按需预览；组件卸载会释放 Object URL。附件被保留策略淘汰后显示明确错误，不触发重建或主线程扫描。

### 11.31 服务端后台命令

- **权限与入口**：`AdminConsoleHandler` 的全部 `/api/admin/server-console*` 路由复用 `WebAuthAdminCheck`，仅 actor 绑定的 admin grant 或在线 OP 可调用。前端 `ServerConsolePanel` 只作为 `AdminPage` 内部标签，不进入全局导航，并通过 `React.lazy` 仅在首次打开标签时下载独立 chunk。
- **执行边界**：`AdminCommandService` 去除可选前导 `/`，限制单行 512 字符、每 actor 750ms 冷却、全局 single-flight，并在 `HandlerTick` queueDepth≥128 时拒收。命令通过合成 `ICommandSender` 在已有 `serverTasks` 阶段执行，捕获聊天输出；停服、封禁、OP、白名单等命令必须携带 `confirmed=true`。HTTP 最多等待 8 秒，超时只表示结果待定，绝不重复入队。
- **玩家与带宽**：玩家端点只复制 `PlayerInfoStore` 已有元数据并复用 3 秒；在线/离线/全部与搜索在前端本地完成。bootstrap 审计只含 160 字符预览，完整输出由详情端点按需取，避免页面打开时传输全部历史。
- **既有管理汇总降载**：`useAdminPlayers` 仅在「玩家网络」标签活跃时轮询 `/api/admin/players`，间隔由 10 秒放宽到 30 秒；切到服务端后台或其他标签后立即停止，避免重型快照统计常驻。
- **持久化**：`AdminConsoleStore` 将最多 64 条共享 preset 与 40 条审计写入 `TeXTech/WebAE/admin-console.json`；每条输出仅保留最后 24×256 字符。快照复制、Gson 序列化和文件 I/O 均在 daemon 中进行，250ms 合并突发保存，不增加空闲 tick 或常驻轮询。
- **诊断**：路由统一经过 `WebApiRouter.route()`，动态 preset/history ID 规范化为稳定 path，自动出现在 diagnostics `topRoutes`/`slowHttp`；主线程命令耗时同时计入既有 `serverTasks` 阶段，无新增 tick phase。

## 12. 前端资源

前端源码位于项目根目录 `webae-frontend/`（React + TypeScript + Ant Design + Vite），构建产物输出到 `src/main/resources/assets/textech/webae/`，由 NanoHTTPD 直接提供。此目录在客户端不需要（@SideOnly 无要求），仅用于服务端 HTTP 服务。

构建产物清单（Vite 打包，contenthash 文件名）：
- `index.html` — SPA 入口，引用 hashed JS/CSS + PWA meta
- `manifest.webmanifest` — PWA manifest（Phase 12）
- `assets/index-[hash].css` — 全局样式 + 高级/极简模式特效层
- `js/index-[hash].js` — 主 bundle（页面组件 + i18n + context + utils）
- `js/antd-[hash].js` — Ant Design + icons（~1.1MB，gzip ~353KB）
- `js/react-[hash].js` — React + ReactDOM（按需 chunk）
- `js/gridstack-[hash].js` — GridStack（tree-shaken）

总 gzip 体积约 450KB，完全离线打包（无 CDN 依赖）。构建命令：`cd webae-frontend && npm install && npm run build`。

## 13. 调试与故障排查

| 问题 | 可能原因 | 检查 |
|------|---------|------|
| 启动后 `localhost:8090` 无响应 | `enabled=false` | 检查 `config/textech/textech.cfg` `[webConsole] enabled` |
| 端口占用 | 其他服务占用 8090 | 修改 `port` 配置 |
| 认证失败 (401) | Token 过期或被撤销 | 运行 `/textech web issue` 重新生成；查看 `code` 字段（`token_expired` vs `invalid_token`） |
| 刷新返回 403 | 非 OP 调用管理员刷新 | 改用游戏内 `/textech web refresh` |
| 存储/电力短暂为空 | 缓存冷启动 | 等待一个 `refreshIntervalMs` 周期；调度器只采集活跃网络 |
| 存储/电力持续为空 | AE2 网络未连接或无活跃网络 | 打开网页控制台/选择网络，让 `SnapshotScheduler.markActive` 运行 |
| 配方搜索无结果 | 未上传 / 未点「获取配方」/ IndexedDB 空 / 用了 displayName 精确搜索 | OP `/textech web recipes upload snapshot`（或 `upload`）后，网页配方页点「获取配方」；开启 `[debug] debugWebae=true` 查看 NEI 采集日志 |
| 图标显示为文字缩写 | 认证失败 / pack 名不一致 / itemId 格式不匹配 | v3.0 已修复：`WebAuthMiddleware` 支持 `?token=` query 参数回退，前端 Icon 组件自动拼接 token；确认 `AeSnapshotCollector` 用 registry name；检查 `TeXTech/WebAE/icons/default-pack.txt` |
| 聊天消息不显示 | 未上传或 Token 无 playerUuid | 确认 `ChatMessageStore` 已持久化 `web-chat.json`；检查 `/api/chat/since` 响应；游戏内消息需 `sendChatMsg` 广播 |
| 玩家头像回退首字母 | 离线模式或 GameProfile 无 textures | `SkinUrlResolver` 对离线玩家返回 null 属正常；正版玩家检查 GameProfile textures property |
| CountDownLatch 超时 (503) | 主线程过载 | 增大超时参数或检查 `HandlerTick` 任务积压 |
| GT 机器列表为空 | `GtCompat` 未启用 | 检查是否安装了 GTNH GT 模组 |
